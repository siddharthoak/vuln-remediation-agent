How It Works

A walkthrough of the pipeline, end to end -- from a raw scanner finding to a merge-ready pull request. Built for narrating live in a demo: read it top to bottom, or jump straight to the Pipeline tab to see it running against live data.

Trivy/Grype scan a Java repo for known CVEs. Each finding is classified into one of four risk buckets. An LLM agent bumps the dependency and fixes what breaks. A pull request opens -- deterministic branch, no duplicates. The Watcher polls CI and retries automatically on failure. CI passes. A human reviews and merges -- nothing merges itself.
The pipeline at a glance

Two independent processes, not one: the Fixer writes the code and opens the PR, then gets out of the way. The Watcher -- a separate, always-on process that never touches code -- takes over from there: it's the one polling CI and deciding whether to retry.

This is the exact sequence a real finding goes through -- the Pipeline tab is a live, counted snapshot of this same diagram.

1Scan ingested

Trivy, Grype, and OWASP Dependency-Check reports (whichever are present in scan-reports/) get parsed and deduplicated into findings -- component, current version, recommended version, severity, CVE ids -- keyed on (component, current_version). Trivy's fix version wins over Grype's over OWASP DC's, since OWASP DC frequently can't compute a safe version at all.

2Classified into a bucket

A pure-Python classifier -- no LLM, no network call -- buckets every finding. Bucket 1: no safe version known, straight to a GitHub triage issue, the Fixer never runs. Bucket 2: a patch/minor bump, or a major bump on a component not flagged complex -- the Fixer runs directly. Bucket 3: a major bump where a Knowledge Base entry already exists -- runs with that migration knowledge injected into the prompt. Bucket 4: a major bump to a hardcoded "complex framework" (Spring Boot, Hibernate, Struts, JSF...) with no KB entry -- also a triage issue, since the risk of a wrong auto-fix is judged too high without ground truth.

This is a cost and risk control, not just a routing table -- every Bucket 2/3 finding costs a real LLM tool-use loop.

3Fixer -- an LLM tool-use loop

The version bump itself is deterministic XML parsing -- the LLM never touches pom.xml directly. Everything else goes to a Gemini tool-use loop with four tools: grep the codebase, read a file, apply an exact-match edit (the find string must be verbatim text the model already read -- the main guardrail against hallucinated edits), and compile. It loops on compiler errors up to 10 rounds (a fixed constant in code_fixer.py, not env-configurable).

{% if run_tests_enabled %}

Test running is turned on (RUN_TESTS=1) -- a fifth tool, run_maven_test, is available once compilation succeeds. The model runs the suite, and on failure diagnoses and corrects it -- writing or updating a test when the failure reveals a genuine behavioral gap the upgrade introduced, not just to force a red test green. This is still prompt-instructed, the same enforcement level compilation itself already has -- nothing mechanically blocks a PR if the model doesn't get there.

{% else %}

Compilation success is the only automated gate before a PR opens today -- there's no test run, no lint, no review pass. An opt-in test-run tool exists (RUN_TESTS=1, only for the default adk engine) but isn't enabled on this deployment.

{% endif %}

Up to {{ max_parallel_fixes }} findings run through this loop in parallel via a thread pool, each against its own local clone.

4Pull request opens

Branch names are deterministic -- hashed from component@version -- so re-running the pipeline for the same vulnerability always produces the same branch and never opens a duplicate PR; if one's already open (or even closed), the Fixer re-attaches to it instead. Every finding gets a tracking record that moves CREATED → PR_OPENED → CI_PENDING -- the single audit trail every tab in this dashboard reads from.

5Watcher takes over -- fully on its own

The Fixer's job ends the moment the PR opens. From here a separate, always-on process -- the Watcher, which never touches code, never clones a repo, never calls the LLM that writes fixes -- runs on its own timer, polling every open fix/* PR every {{ watcher_sleep_minutes }} minutes by default. No one has to trigger this; it's the same background loop whether or not anyone's watching the dashboard.

CI pass marks the record CI_PASSED and mines the diff for the exact patterns used, so the next time this exact upgrade comes up, the system uses a confirmed pattern instead of guessing again. CI failure hands off to the retry gate below -- still entirely the Watcher's call, not the Fixer's.

6Retry gate, then a human

On CI failure, the retry gate -- the only place in the whole system that decides retry-vs-give-up -- checks how many attempts this PR has already had. Under the limit ({{ max_retry_attempts }} by default), it writes a RETRY_REQUESTED record with the CI failure log attached and calls the Fixer's retry endpoint, which puts that log at the very top of the prompt so the model diagnoses root cause instead of repeating the first attempt. At the limit, it marks FAILED_MAX_RETRIES and posts an escalation comment -- automation stops, a human takes over.

Nothing in this system merges a PR itself, ever -- CI_PASSED is the final automated state. A human reviews and merges like any other PR.
